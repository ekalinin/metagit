# Design

## Context

Проект новый: кода нет, существующих спецификаций нет. Мотивация и объем - в `proposal.md`, требования - в `specs/`.

Ограничения, которые задают подход:
- Один владелец, self-hosted, один сервер.
- Go для сервера, TypeScript для веб-интерфейса.
- Вся работа с репозиториями идет через системный git. На сервере также нужен системный `ssh`-клиент для доставки на target'ы по SSH.
- git позволяет отклонить push только на этапе `pre-receive`. На этом этапе новые объекты лежат в карантине и видны только процессу хука, а обновлять refs из карантина git запрещает.

## Goals / Non-Goals

**Goals:**
- Установка - один бинарник плюс git и ssh на сервере.
- Ядро доставки не зависит от хостинга и работает с любым git URL.
- Сбой процесса в любой момент не приводит к потере архива и не оставляет target'ы в неизвестном состоянии: после перезапуска все догоняется сверкой.
- Поведение проверяется интеграционными тестами с настоящим git.

**Non-Goals:**
- Высокая доступность и несколько экземпляров metagit на одних данных.
- Собственная реализация git-протокола.
- Поддержка Windows как серверной платформы.

## Decisions

### 1. Один бинарник Go, системный git

```
 +----------------------------- metagit serve ---------------------------------+
 |                                                                             |
 |  HTTP :8080                       SSH :2222                                 |
 |   |-- /api/*      JSON API         |-- exec git-upload-pack / receive-pack  |
 |   |-- /<p>.git/*  git http-backend |                                        |
 |   |-- /*          SPA (embed)      |                                        |
 |   |                                |                                        |
 |   +---------------+----------------+                                        |
 |                   v                                                         |
 |        системный git (bare repo) --> хуки --> "metagit hook ..."            |
 |                                                    |                        |
 |                                     unix-сокет внутреннего API              |
 |                                                    v                        |
 |   SQLite <--> ядро: защита refs, архив, очередь доставки                    |
 |                                                    |                        |
 |                                       воркер на каждый target               |
 |                                                    v                        |
 |                          git push / ls-remote / fetch на хостинги           |
 +-----------------------------------------------------------------------------+
```

Подкоманды бинарника:
- `metagit serve` - сервис.
- `metagit owner create` - создать владельца или сменить ему пароль, работает только на сервере.
- `metagit hook <pre-receive|post-receive>` - вызывается git-хуками.
- `metagit askpass` - выдает учетные данные HTTPS-target'а процессу git.

Альтернативы:
- **go-git** избавил бы от внешней зависимости, но серверную часть, хуки, карантин и `--force-with-lease` пришлось бы воспроизводить самим. Решение принято в обсуждении.
- **Gitea/Forgejo как основа** - это полноценный forge с лишней для нас функциональностью, а его push mirrors используют `push --mirror`, что противоречит требованиям.

### 2. Каталог данных

```
<data>/
  metagit.db              SQLite
  secret.key              мастер-ключ шифрования (если не задан через окружение)
  ssh_host_ed25519_key    ключ SSH-сервера, создается при первом запуске
  known_hosts             ключи хостингов для доставки по SSH
  hooks/pre-receive       #!/bin/sh  exec "<путь к metagit>" hook pre-receive
  hooks/post-receive      #!/bin/sh  exec "<путь к metagit>" hook post-receive
  repos/<project>.git     bare-репозитории
  tmp/                    временные файлы ключей, права 0700
```

Каждый репозиторий создается командой `git init --bare` с настройками `core.hooksPath=<data>/hooks` и `core.logAllRefUpdates=always`. Reflog в bare-репозитории удерживает старые объекты, пока архивный ref не создан, даже если между push и архивом случился сбой.

`receive.fsckObjects` намеренно не включается: старые реальные репозитории часто содержат исторические ошибки fsck (например, некорректные даты автора), и такая проверка отклонила бы их push. metagit должен принимать и зеркалировать существующие проекты.

Скрипты хуков перезаписываются при каждом старте `serve`. Так путь к бинарнику остается верным после обновления.

### 3. Хранилище: SQLite без cgo

Используется SQLite через драйвер на чистом Go (`modernc.org/sqlite`), поэтому бинарник собирается статически. Миграции встроены в бинарник и применяются при старте.

Таблицы:

| Таблица | Назначение |
|---|---|
| `owner` | имя, хеш пароля |
| `sessions` | сессии веб-интерфейса |
| `access_tokens` | токены для git по HTTP: имя, SHA-256 значения, даты |
| `ssh_keys` | публичные SSH-ключи владельца, отпечатки |
| `projects` | имя, дата создания |
| `protected_refs` | проект, шаблон |
| `targets` | проект, имя, URL, вид учетных данных, зашифрованный секрет, включен ли, состояние, последняя ошибка, время последней успешной доставки, время следующей попытки, номер попытки |
| `target_refs` | target, ref, объект: что metagit последним доставил или подтвердил на target'е |
| `archive_intents` | проект, ref, прежний объект, создан ли архив |
| `archive_refs` | проект, источник (push/target), id target'а, исходный ref, архивный ref, объект, время |
| `events` | проект, target, вид, текст, время |

Файл базы создается с правами 0600 (у существующего права выставляются при открытии): в нем зашифрованные секреты и хеш пароля. SQLite дает файлам `-wal` и `-shm` права файла базы.

Альтернативы: `mattn/go-sqlite3` требует cgo. PostgreSQL избыточен для одного владельца и усложняет установку.

### 4. Git по HTTP через `git http-backend`

Go-обработчик проверяет HTTP Basic auth: пароль - токен владельца, сравнивается SHA-256 от него. Затем запрос передается в `git http-backend` через `net/http/cgi` с окружением `GIT_PROJECT_ROOT=<data>/repos`, `GIT_HTTP_EXPORT_ALL=1` и `REMOTE_USER=<owner>`. Когда задан `REMOTE_USER`, `http-backend` сам разрешает `receive-pack`.

`net/http/cgi` отклоняет тела запросов с `Transfer-Encoding: chunked`, а git отправляет так push больше 1 МиБ. Поэтому такое тело сначала записывается во временный файл в `<data>/tmp`, и в `http-backend` оно уходит с известной длиной. После запроса файл удаляется.

Маршрутизация: пути вида `/<project>.git/...` уходят в git, `/api/` - в API, все остальное - в SPA.

Альтернатива: своя реализация поверх `git upload-pack --stateless-rpc`, как в Gitea. Это больше кода, а выгоды для одного владельца нет. `http-backend` - стандартный компонент git и уже поддерживает protocol v2.

### 5. Git по SSH: встроенный сервер

Используется `golang.org/x/crypto/ssh`, порт по умолчанию 2222. Аутентификация - только по публичным ключам из `ssh_keys`. Принимаются только запросы `exec` с командой `git-upload-pack '<path>'` или `git-receive-pack '<path>'` (также с пробелом вместо дефиса). Путь приводится к проекту, после чего запускается системный git с stdin/stdout/stderr канала и возвратом `exit-status`. Любые другие запросы (`shell`, `pty-req`, другие команды) отклоняются.

Альтернативы:
- Системный `sshd` с `command=` в `authorized_keys` требует настройки сервера под root и ломает идею одного бинарника.
- `gliderlabs/ssh` - удобная обертка, но лишняя зависимость: `x/crypto/ssh` достаточно.

### 6. Хуки и внутренний API

Процесс `serve`, запуская git (из HTTP или SSH), передает в окружение `METAGIT_SOCKET` (путь к unix-сокету), `METAGIT_PROJECT` и одноразовый `METAGIT_PUSH_ID`. git передает окружение хукам.

**pre-receive** (`metagit hook pre-receive`):
1. Читает строки `old new ref` из stdin.
2. Сам классифицирует каждое изменение: создание, fast-forward, не fast-forward, удаление, перемещение тега. Для проверки предка вызывается `git merge-base --is-ancestor old new`. Это делает именно процесс хука: только его окружение видит объекты из карантина.
3. Отправляет классифицированный список в сервис по сокету.
4. Сервис отклоняет push целиком, если затронут `refs/metagit/*` или защищенный ref с разрушающим изменением. Иначе он записывает в `archive_intents` прежние значения для разрушающих изменений и разрешает push.
5. Хук печатает ответ сервиса и завершается с его кодом.

**post-receive** (`metagit hook post-receive`):
1. Сообщает сервису, что push завершен.
2. Сервис выполняет намерения этого push: если ref уже не равен прежнему значению, создает архивный ref командой `git update-ref <archive> <old> ""` (только если имени еще нет) и пишет запись в `archive_refs` и событие.
3. Сервис помечает проект как измененный для всех включенных target'ов и ждет их результатов не дольше `push-status-timeout`.
4. Хук печатает по строке на каждый target. git показывает их клиенту с префиксом `remote:`.

При старте сервис выполняет все незавершенные `archive_intents`. Если push в итоге не прошел (ref равен прежнему значению), намерение закрывается без архива.

Альтернатива: хук работает с SQLite напрямую. Тогда логику пришлось бы дублировать в двух процессах, и post-receive не смог бы дождаться результатов доставки.

### 7. Доставка как сверка состояния

Доставка не воспроизводит события, а сводит target к текущему состоянию metagit:

```
 желаемое  = git for-each-ref refs/heads refs/tags   (в репозитории metagit)
 известное = target_refs для этого target'а

 для каждого ref из желаемого, где объект != известному   -> обновить
 для каждого ref из известного, которого нет в желаемом   -> удалить
 refs на хостинге вне "известного" и "желаемого"          -> не трогать
```

Так несколько быстрых push'ей сливаются в одну доставку, а после сбоя достаточно повторить сверку.

Одна сверка выполняется одной командой:

```
git push --porcelain \
  --force-with-lease=<ref>:<известный объект или пусто> ...  \
  <url> <объект>:<ref> ... :<удаляемый ref> ...
```

Пустое значение в `--force-with-lease=<ref>:` означает "ref на хостинге не должен существовать". По выводу `--porcelain` каждый ref разбирается отдельно:
- **принят** - обновить `target_refs`;
- **отклонен из-за lease** - обработка расхождения (ниже);
- **другая ошибка** - состояние "ошибка", следующая попытка по расписанию. К тексту ошибки добавляются сообщения хостинга из stderr (строки `remote: ...`, не больше 20): они объясняют причину отказа, например защиту ветки на хостинге. Текст проходит маскировку секретов (раздел 8).

`--atomic` не используется: не все хостинги его поддерживают, а частичный прогресс допустим, потому что сверка идемпотентна.

**Обработка расхождения для ref** (не больше 3 итераций за одну сверку, потом ошибка):
1. `git ls-remote <url> <ref>` возвращает текущий объект X на хостинге.
2. Если X равен желаемому объекту, записать X в `target_refs` и закончить.
3. Если X есть в репозитории metagit и является предком желаемого объекта, повторить push с lease на X, без архива и без события.
4. Иначе выполнить `git fetch <url> <ref>`, создать архивный ref `refs/metagit/archive/targets/<id>/<ref>/<время>` на X, записать событие "расхождение" и повторить push с lease на X.

**Конкурентность:** у каждого target'а один воркер с флагом "нужна сверка", поэтому повторные сигналы сливаются. Target'ы обрабатываются параллельно, число одновременных доставок ограничено настройкой (по умолчанию 4).

**Когда запускается сверка:** после post-receive, при добавлении или включении target'а, по кнопке "доставить сейчас", по таймеру повтора и при старте сервиса для target'ов в состоянии "ожидает" или "ошибка".

**Повторы:** интервал растет экспоненциально от 15 секунд до 30 минут, со случайным разбросом.

**Таймаут:** у каждой git-операции на хостинге свой таймаут, по умолчанию 10 минут.

### 8. Учетные данные target'ов при вызове git

Общее окружение: `GIT_TERMINAL_PROMPT=0` и `-c credential.helper=`, чтобы системные помощники учетных данных не вмешивались.

- **HTTPS:** `GIT_ASKPASS=<путь к metagit>` (подкоманда `askpass`), логин и токен передаются через переменные окружения дочернего процесса. Токен не попадает ни в URL, ни в аргументы командной строки.
- **SSH:** ключ записывается во временный файл в `<data>/tmp` с правами 0600 и удаляется после операции. Команда: `GIT_SSH_COMMAND="ssh -i <файл> -o IdentitiesOnly=yes -o BatchMode=yes -o UserKnownHostsFile=<data>/known_hosts -o StrictHostKeyChecking=accept-new"`.

Весь вывод git перед записью в события, журналы и вывод push проходит через маскировку: из него вырезаются известные секреты и userinfo из URL.

### 9. Шифрование секретов

Секреты target'ов шифруются AES-256-GCM мастер-ключом. Ключ берется из `METAGIT_SECRET_KEY`, а если переменная не задана, из `<data>/secret.key`. Файл создается при первом запуске с правами 0600.

Альтернатива: ключ из пароля владельца. Тогда сервис не смог бы работать без ввода пароля после перезапуска, а для асинхронной доставки это неприемлемо.

### 10. Вход владельца и защита веб-интерфейса

- Пароль хранится как argon2id-хеш.
- Сессия - случайный идентификатор в cookie `HttpOnly`, `SameSite=Strict`, с флагом `Secure` при TLS.
- API принимает изменения только с `Content-Type: application/json`, в дополнение к `SameSite` против CSRF.
- Вход ограничен по частоте попыток с одного адреса.
- Токены для git: 32 случайных байта с префиксом `mgt_`, в базе хранится только SHA-256.

### 11. Веб-интерфейс

TypeScript, Vite, React. Это допущение: конкретный фреймворк не обсуждался. Сборка лежит в `web/dist`, встраивается в бинарник через `embed` и отдается как SPA. Обмен с сервером - JSON API `/api/...`.

### 12. Экспорт и импорт

Экспорт - JSON с полем `version`, зашифрованный форматом age с паролем (`filippo.io/age`, scrypt). Файл можно расшифровать и стандартной утилитой `age -d`, без metagit.

Альтернатива: своя схема scrypt + AES-GCM. Это больше кода и непроверенный формат.

Импорт:
1. Расшифровать и проверить файл.
2. Проверить конфликты имен.
3. Создать все записи в одной транзакции SQLite.
4. Создать bare-репозитории. При ошибке созданные репозитории удаляются, а транзакция откатывается.

`target_refs` после импорта пуст. Поэтому metagit ничего не удаляет на хостингах, а первый push проходит через обработку расхождения, как требует `settings-transfer`.

### 13. Настройки сервиса

Флаги с аналогами в переменных окружения `METAGIT_*`:

| Флаг | По умолчанию |
|---|---|
| `--data-dir` | `./data` |
| `--http-addr` | `:8080` |
| `--ssh-addr` | `:2222` |
| `--base-url` | для показа адресов клонирования |
| `--ssh-url` | для показа адресов клонирования |
| `--tls-cert`, `--tls-key` | не заданы; без них предполагается reverse proxy с TLS |
| `--push-status-timeout` | `5s` |
| `--max-parallel-deliveries` | `4` |

### 14. Раскладка кода

```
cmd/metagit/          main и подкоманды
internal/config/      флаги и окружение
internal/store/       SQLite, миграции, запросы
internal/secrets/     мастер-ключ, AES-GCM, маскировка
internal/auth/        владелец, сессии, токены, SSH-ключи
internal/gitcmd/      запуск системного git, разбор вывода
internal/repo/        создание и удаление bare-репозиториев, хуки
internal/githttp/     git по HTTP
internal/gitssh/      git по SSH
internal/hooks/       внутренний API и клиент хуков
internal/archive/     намерения и архивные refs
internal/replicate/   воркеры, сверка, расхождения, повторы
internal/transfer/    экспорт и импорт
internal/api/         JSON API
web/                  Vite + React + TypeScript
```

Ядро доставки (`internal/replicate`) работает только с URL и учетными данными. Адаптеры хостингов (создание репозиториев через API) в будущем смогут подключаться на этапе создания target'а, не затрагивая доставку.

### 15. Тестирование

Интеграционные тесты используют настоящий git. "Хостинг" в тестах - `httptest`-сервер с `git http-backend` над временным bare-репозиторием. Так проверяются доставка, lease, расхождения и чужие ветки без внешних сервисов и без специальных разрешений для `file://`. Для SSH-доступа к metagit тесты используют SSH-клиент git со сгенерированным ключом.

## Risks / Trade-offs

- [Мастер-ключ лежит на том же диске, что и база] → Шифрование защищает от утечки одной базы (например, из резервной копии), но не от полного доступа к серверу. В документации рекомендуется задавать ключ через `METAGIT_SECRET_KEY` из внешнего хранилища секретов и запускать metagit под отдельным пользователем.
- [На хостинге включена своя защита веток, запрещающая force-push] → Доставка ref получает ошибку, target переходит в состояние "ошибка" с понятным текстом. Владелец меняет настройки на хостинге.
- [Расхождение на хостинге обнаруживается только при следующей доставке] → Для одной копии это допустимо: изменения на хостинге не теряются, они попадут в архив при следующей перезаписи. Периодическая проверка вынесена в открытые вопросы.
- [Кто-то постоянно пушит на хостинг в обход metagit] → Не больше 3 итераций обработки расхождения за сверку, затем состояние "ошибка".
- [Архив растет бесконечно] → Размер и список архива видны в веб-интерфейсе. Очистка вынесена в открытые вопросы.
- [Сбой между push и созданием архива] → `archive_intents` и `core.logAllRefUpdates=always`. Reflog удерживает объекты, а намерение выполняется при старте.
- [Разные версии git и ssh на серверах] → При старте `serve` проверяет наличие и версию git и ssh. Интеграционные тесты в CI идут на зафиксированной версии git.
- [Открытый SSH-порт и страница входа видны из сети] → SSH принимает только ключи и только git-команды. Вход по паролю с argon2id и ограничением частоты попыток.
- [Секреты в окружении дочерних процессов git видны процессам того же пользователя] → Запуск metagit под отдельным системным пользователем, это есть в документации.

## Migration Plan

Проект новый, миграции данных нет. Развертывание:
1. Собрать бинарник (сборка веб-интерфейса, затем `go build`).
2. Установить на сервер git и ssh-клиент.
3. Выполнить `metagit owner create --data-dir ...`.
4. Запустить `metagit serve` под отдельным пользователем, при необходимости за reverse proxy с TLS.

Откат: остановить сервис. Каталог данных совместим с повторным запуском той же версии. Миграции схемы применяются только вперед.
