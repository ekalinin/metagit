# mirror-replication Specification

## Purpose

metagit асинхронно доставляет ветки и теги каждого проекта на все target'ы, которые настроил владелец. Чужие refs на хостингах он не трогает, а изменения, сделанные на хостинге в обход metagit, не теряются.

## Requirements

### Requirement: Настройка target'а
Владелец SHALL иметь возможность добавить к проекту target: имя, URL git-репозитория и учетные данные одного из видов - без учетных данных, логин и токен для HTTPS или приватный SSH-ключ. metagit MUST принимать любой URL со схемой `https` или `ssh` либо в виде `user@host:path`, независимо от хостинга. metagit MUST отклонять URL, в котором есть пароль или токен. Target можно выключить: выключенному target'у metagit ничего не доставляет.

#### Scenario: Первая доставка на новый target
- **WHEN** владелец добавляет target к проекту, в котором есть ветки и теги
- **THEN** metagit доставляет на target все ветки и теги проекта

#### Scenario: URL с секретом
- **WHEN** владелец указывает URL вида `https://user:token@github.com/u/foo.git`
- **THEN** metagit отклоняет target и предлагает передать токен в учетных данных

#### Scenario: Выключенный target
- **WHEN** target выключен, и владелец делает push в проект
- **THEN** metagit не обращается к этому target'у

### Requirement: Асинхронная доставка
Push в metagit MUST завершаться успешно, как только metagit сохранил изменения у себя, независимо от доступности и ответов target'ов. metagit MUST доставлять изменения на каждый включенный target в фоне.

#### Scenario: Хостинг недоступен
- **WHEN** один из target'ов недоступен, и владелец делает push в metagit
- **THEN** push завершается успешно, а доставка на недоступный target ставится в очередь на повтор

### Requirement: Доставляются только ветки и теги metagit
metagit MUST доставлять только refs `refs/heads/*` и `refs/tags/*`. metagit MUST NOT создавать, менять или удалять на target'е refs с именами, которых нет среди веток и тегов проекта, кроме удаления ref, который metagit сам доставил ранее и который потом был удален в metagit.

#### Scenario: Ветка, созданная только на хостинге
- **WHEN** на target'е есть ветка `pr-branch`, которой никогда не было в metagit, и metagit доставляет изменения на этот target
- **THEN** ветка `pr-branch` на target'е остается без изменений

#### Scenario: Удаление ветки в metagit
- **WHEN** metagit ранее доставил ветку `old` на target, и владелец удаляет `old` в metagit
- **THEN** metagit удаляет `old` на target'е

#### Scenario: Прочие пространства refs
- **WHEN** в репозитории metagit есть refs вне `refs/heads/` и `refs/tags/`
- **THEN** metagit не доставляет их на target'ы

### Requirement: Target повторяет состояние metagit
После успешной доставки каждая ветка и каждый тег проекта на target'е MUST указывать на тот же объект, что и в metagit, в том числе после force-push в незащищенную ветку. Если несколько push'ей пришли до завершения доставки, промежуточные состояния могут не попасть на target, но target MUST в итоге получить последнее.

#### Scenario: Force-push в незащищенную ветку
- **WHEN** metagit ранее доставил `feature` = C на target, а владелец сделал force-push `feature` = D в metagit
- **THEN** после доставки `feature` на target'е указывает на D

#### Scenario: Несколько push подряд
- **WHEN** владелец делает три push в `main` подряд, пока доставка на target еще идет
- **THEN** после завершения доставки `main` на target'е указывает на последний коммит

### Requirement: Расхождение на target'е
metagit MUST считать ref на target'е разошедшимся, если он указывает не на тот объект, который metagit доставил туда последним (или существует, хотя metagit его туда не доставлял), и этот объект не содержится в истории нового значения ref в metagit. Для разошедшегося ref metagit MUST:
1. Сохранить текущее значение ref на target'е в архив (см. `ref-archive`).
2. Перезаписать ref на target'е значением из metagit или удалить его, если ref удален в metagit. Перезапись или удаление выполняется только при условии, что ref на target'е все еще указывает на сохраненное в архив значение. Если ref на target'е успел измениться снова, шаги повторяются.
3. Записать событие "расхождение" с именем target'а, ref и архивного ref, видимое в веб-интерфейсе.

Если ref на target'е уже указывает на тот же объект, что и в metagit, или на объект, который содержится в истории нового значения, metagit MUST обновить ref без архива и без события расхождения.

#### Scenario: Merge в веб-интерфейсе хостинга
- **WHEN** metagit доставил `main` = C на GitHub, на GitHub сделали merge и `main` стал E, а затем владелец сделал push `main` = D (потомок C, но не E) в metagit
- **THEN** E сохраняется в архив metagit, `main` на GitHub указывает на D, и в веб-интерфейсе появляется событие расхождения с именем архивного ref

#### Scenario: Совпадающая ветка с таким же именем
- **WHEN** на target'е уже есть `main` = C, metagit его туда не доставлял, а в metagit `main` = C
- **THEN** metagit считает `main` доставленным, не создает архив и не пишет событие расхождения

#### Scenario: Ветка на хостинге отстает
- **WHEN** на target'е `main` = B, metagit его туда не доставлял, а в metagit `main` = C, потомок B
- **THEN** metagit обновляет `main` на target'е до C без архива и без события расхождения

### Requirement: Повторы и статус доставки
При неудачной доставке metagit MUST повторять попытки автоматически с растущим интервалом. Для каждого target'а metagit MUST хранить состояние доставки: "синхронизирован", "ожидает" или "ошибка" с текстом последней ошибки, а также время последней успешной доставки. Владелец SHALL иметь возможность запустить доставку на target вручную.

#### Scenario: Временная ошибка хостинга
- **WHEN** target отвечает ошибкой при доставке
- **THEN** состояние target'а становится "ошибка" с текстом ошибки, и metagit повторяет попытку позже

#### Scenario: Хостинг снова доступен
- **WHEN** target с состоянием "ошибка" снова принимает данные
- **THEN** очередная попытка доставляет все изменения, и состояние становится "синхронизирован"

### Requirement: Статус доставки в выводе push
После того как metagit принял push, он MUST ждать результатов доставки на включенные target'ы не дольше настраиваемого времени (по умолчанию 5 секунд). Для каждого target'а metagit MUST вывести строку в вывод push: `delivered`, расхождение (`diverged` с именем архивного ref), ошибка (`error` с кратким текстом и пометкой `retry later`) или `queued`, если результат не получен за отведенное время. Строки вывода push MUST быть на английском. Ожидание MUST NOT менять результат push.

#### Scenario: Все target'ы ответили быстро
- **WHEN** владелец делает push, и все target'ы принимают изменения за 2 секунды
- **THEN** в выводе push есть строка `delivered` для каждого target'а

#### Scenario: Медленный target
- **WHEN** один target не ответил за отведенное время
- **THEN** для него в выводе push есть строка `queued`, push завершается после истечения времени ожидания, а доставка продолжается в фоне

#### Scenario: Ошибка доставки в выводе push
- **WHEN** доставка на target `bitbucket` завершилась ошибкой за отведенное время
- **THEN** в выводе push есть строка `bitbucket: error:` с кратким текстом ошибки и пометкой `(retry later)`

### Requirement: Защита учетных данных target'ов
metagit MUST хранить учетные данные target'ов в зашифрованном виде. metagit MUST NOT показывать сохраненные учетные данные в веб-интерфейсе и API и MUST NOT выводить их в журналы, события и вывод push.

#### Scenario: Просмотр target'а
- **WHEN** владелец открывает настройки target'а с сохраненным токеном
- **THEN** веб-интерфейс показывает, что токен задан, но не показывает его значение

#### Scenario: Ошибка доставки с токеном в URL запроса
- **WHEN** доставка завершается ошибкой, и в тексте ошибки git есть учетные данные
- **THEN** в событии и в выводе push учетные данные заменены маской
