# git-hosting Specification

## Purpose

metagit выглядит для разработчика как обычный git remote: хранит каждый проект как git-репозиторий, принимает push и отдает clone и fetch по HTTP(S) и SSH, но только владельцу.

## Requirements

### Requirement: Проект как git-репозиторий
Владелец SHALL иметь возможность создать проект с уникальным именем. Имя состоит из символов `a-z`, `0-9`, `.`, `_`, `-`. Для нового проекта metagit MUST создать пустой git-репозиторий, доступный по адресам `<base-url>/<project>.git` (HTTP(S)) и `ssh://<host>:<ssh-port>/<project>.git` (SSH).

#### Scenario: Создание проекта
- **WHEN** владелец создает проект `foo`
- **THEN** `git clone <base-url>/foo.git` с учетными данными владельца клонирует пустой репозиторий

#### Scenario: Имя уже занято
- **WHEN** владелец создает проект с именем существующего проекта
- **THEN** metagit отклоняет создание и не меняет существующий проект

#### Scenario: Недопустимое имя
- **WHEN** владелец создает проект с именем, содержащим `/` или заглавные буквы
- **THEN** metagit отклоняет создание с сообщением о допустимых символах

### Requirement: Доступ к git по HTTP(S)
metagit MUST поддерживать clone, fetch и push по git smart HTTP. Каждый git-запрос по HTTP MUST быть авторизован токеном доступа владельца, переданным через HTTP Basic auth.

#### Scenario: Push с действующим токеном
- **WHEN** владелец делает `git push` по HTTP(S) с действующим токеном
- **THEN** metagit принимает изменения

#### Scenario: Запрос без токена или с неверным токеном
- **WHEN** git-клиент обращается к репозиторию без токена или с неверным либо отозванным токеном
- **THEN** metagit отвечает 401 и не отдает и не принимает данные репозитория

#### Scenario: Несуществующий проект
- **WHEN** авторизованный git-клиент обращается к проекту, которого нет
- **THEN** metagit отвечает ошибкой `repository not found`

### Requirement: Доступ к git по SSH
metagit MUST поддерживать clone, fetch и push по SSH на отдельном порту. Аутентификация MUST проходить по SSH-ключам, которые владелец зарегистрировал в metagit. metagit MUST выполнять только git-команды получения и отправки данных и MUST отклонять любые другие запросы, включая интерактивную оболочку.

#### Scenario: Push с зарегистрированным ключом
- **WHEN** владелец делает `git push` по SSH с ключом, зарегистрированным в metagit
- **THEN** metagit принимает изменения

#### Scenario: Незарегистрированный ключ
- **WHEN** клиент подключается по SSH с ключом, которого нет в metagit
- **THEN** metagit отклоняет аутентификацию

#### Scenario: Запрос оболочки
- **WHEN** клиент с зарегистрированным ключом запрашивает интерактивную оболочку или произвольную команду
- **THEN** metagit отклоняет запрос

### Requirement: Защищенные ветки и теги
Владелец SHALL иметь возможность задать для проекта список шаблонов полных имен refs (например, `refs/heads/main`, `refs/tags/*`). Для ref, подходящего под шаблон, metagit MUST отклонять push, если он не fast-forward, удаляет ref или перемещает существующий тег. При отклонении ни один ref из этого push не меняется, а в выводе push указано имя защищенного ref.

#### Scenario: Force-push в защищенную ветку
- **WHEN** в проекте защищен `refs/heads/main`, и владелец делает `git push --force` в `main` с коммитом, который не содержит текущий `main`
- **THEN** metagit отклоняет push, сообщает, что `refs/heads/main` защищен, и `main` остается прежним

#### Scenario: Удаление защищенной ветки
- **WHEN** в проекте защищен `refs/heads/main`, и владелец делает `git push origin :main`
- **THEN** metagit отклоняет push, и `main` остается прежним

#### Scenario: Перемещение защищенного тега
- **WHEN** в проекте защищен `refs/tags/*`, и владелец делает force-push существующего тега `v1.0` на другой коммит
- **THEN** metagit отклоняет push, и `v1.0` остается прежним

#### Scenario: Fast-forward в защищенную ветку
- **WHEN** в проекте защищен `refs/heads/main`, и владелец делает push в `main` с коммитом-потомком текущего `main`
- **THEN** metagit принимает push

#### Scenario: Force-push в незащищенную ветку
- **WHEN** ветка `feature` не подходит ни под один шаблон, и владелец делает `git push --force` в `feature`
- **THEN** metagit принимает push

### Requirement: Служебное пространство refs
metagit MUST отклонять любые изменения refs в пространстве `refs/metagit/`, которые приходят через git push.

#### Scenario: Push в служебный ref
- **WHEN** владелец делает push в `refs/metagit/archive/anything`
- **THEN** metagit отклоняет push, и служебные refs не меняются
