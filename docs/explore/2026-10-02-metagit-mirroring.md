# metagit: исследование идеи

Статус: исследование, решения еще не приняты.

## Идея

Сервис, который имитирует git, но в нем можно настраивать репозитории реальных хранилищ (GitHub, Bitbucket и т.д.), куда будут "зеркалироваться" коммиты.

Практически, прокси, которая умеет хранить проекты в нескольких публичных системах контроля версий. Снижает риск бана проекта на каком-то хостинге и потери исходников. Способ зеркалировать проект.

## Что значит "имитирует git"

Под "прокси" можно понимать три разные вещи:

```
 A. Сервер-прокси: metagit сам является remote

   dev ---push---> [ metagit  ] ---push---> github
   dev <--clone--- [ bare repo] ---push---> bitbucket
                                ---push---> codeberg

 B. Клиентский инструмент, без сервера

   dev ---[ git + metagit CLI / remote-helper ]---push---> github
                                                ---push---> bitbucket

 C. Демон-зеркальщик: основной репозиторий живет на хостинге

   dev ---push---> github <---poll--- [ metagit ] ---push---> bitbucket
                                                  ---push---> codeberg
```

Судя по формулировке идеи, имеется в виду вариант A: разработчик видит обычный git remote, а все остальное происходит за ним.

## Что уже существует

| Что есть | Тип | Чего не хватает |
|---|---|---|
| `git remote set-url --add --push` (несколько push URL у одного remote) | B | Нет состояния и повторов. Если один хостинг не принял push, зеркала просто разойдутся |
| GitHub Actions (multi-git-mirror, roostorg/mirror) | C | Управление живет на GitHub. Если забанят именно там, вместе с аккаунтом пропадет и механизм зеркалирования |
| Push mirrors в Forgejo/Gitea | A | Ближе всего к идее, но это целый forge. Используется `push --mirror` с force-push, и ветки, созданные только на зеркале (например, для PR), удаляются |
| gickup | C | Резервное копирование по расписанию, а не прокси на запись |

В варианте C основной репозиторий и управление сидят на том самом хостинге, который может забанить. Вариант A (или B) - единственный, где собственная полная копия и управление находятся вне хостингов.

## Модель угроз

| Риск | Помогает? | Комментарий |
|---|---|---|
| Бан аккаунта или санкции на одном хостинге | да | основной сценарий |
| Хостинг закрылся или недоступен | да | |
| DMCA / takedown конкретного репозитория | частично | такое же требование могут отправить и на другие хостинги |
| Ошибочный force-push или удаление ветки | нет, наоборот | простое зеркало разнесет это повреждение по всем копиям |
| Утечка токенов metagit | хуже, чем без него | один узел держит доступ на запись ко всем хостингам |
| Падение самого metagit | зависит от устройства | его нужно уметь восстановить из любого зеркала |

Вывод: зеркало - это не резервная копия. Если цель - "не потерять исходники", metagit должен по-другому обращаться с разрушающими операциями. Например, перед force-push сохранять старый ref в `refs/metagit/archive/...` или вообще не передавать удаления на хостинги без явного подтверждения.

## Вариант A изнутри

Протокол git реализовывать заново почти не нужно. Хватит обычного git (`git http-backend` или ssh + `git-shell`), а самое интересное начинается после `post-receive`:

```
 +--------------------------- metagit -------------------------------+
 |                                                                   |
 |  ssh / smart-http       bare repo          post-receive hook      |
 |  (настоящий git)  ---> refs + objects ---> "refs изменились"      |
 |                                                  |                |
 |                                                  v                |
 |                                   +----------------------------+  |
 |                                   | очередь репликации         |  |
 |                                   | target x ref -> sha,       |  |
 |                                   | попытки, ошибка, политика  |  |
 |                                   +----------------------------+  |
 |                                       |         |          |      |
 +---------------------------------------|---------|----------|------+
                                         v         v          v
                                      github   bitbucket   codeberg
                                       [ok]   [retry 3/5]    [ok]
```

## Гипотезы о ценности metagit

Это гипотезы, а не принятые требования:

1. Легковесность: git endpoint плюс рассылка по хостингам, а не целый forge.
2. Создание репозитория сразу на всех хостингах через их API одной командой.
3. Видно состояние каждого target, есть повторы и обнаружение расхождений.
4. Безопасная политика для force-push и удалений.
5. Восстановление: если metagit умер, его можно поднять из любого живого зеркала.

## Решения, которые зависят друг от друга

```
 [1] где живет и кто пушит  (сервер / локально / SaaS)
        |
        v
 [2] направление синхронизации  (metagit - единственный источник истины
        |                        или PR и коммиты бывают и на GitHub?)
        v
 [3] согласованность  (асинхронно / ждать всех / кворум N из M)
        |
        v
 [4] разрушающие операции  (force-push, удаление веток и тегов)
        |
        v
 [5] что кроме git  (LFS, релизы, issues, wiki)  +  шифрование зеркал?
```

Пункт [2] по сложности различается на порядок. Односторонняя синхронизация простая. Двусторонняя означает разбор конфликтов и полноценный сервис синхронизации.

## Открытые вопросы

### 1. Где живет metagit и кто в него пушит?

- Свой сервер (VPS или домашний), пушит автор и, возможно, команда. Это вариант A.
- Локально у разработчика, без сервера. Это вариант B.
- SaaS для других людей.

От ответа зависит, нужен ли внутри git-сервер, где хранится эталонная копия и как выглядит модель угроз. У SaaS есть ирония: он сам становится хостингом, который может упасть или кого-то заблокировать.

Рекомендация (не решение): self-hosted сервер (A). Только в нем собственная полная копия и управление находятся вне хостингов, которые могут забанить. Для единственного пользователя вариант B подойдет как первая версия: это CLI поверх нескольких push URL, к которому добавлены состояние, повторы и создание репозиториев.

### Другие направления

- Шифрованные зеркала: приватный код на публичных хостингах, в духе `git-remote-gcrypt`.
- p2p-подход вроде Radicle как альтернатива зеркалированию вообще.
